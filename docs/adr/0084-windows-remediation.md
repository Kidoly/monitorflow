# ADR-0084: AI remediation on Windows

Date: 2026-11-03
Status: accepted

## Context

AI remediation (ADR-0043) runs the commands an AI proposes on the server whose alert opened the incident: read-only ones at once, changes after a person approves them, forbidden ones never. Every command is classified by rules written for `/bin/sh` (ADR-0041), and the agent runs it with `/bin/sh -c`. Windows agents refuse `shell` (ADR-0047), because PowerShell parses the same line differently: `$` expands anywhere, a backtick escapes, `;` and `&` separate statements, and aliases change meaning (`sc` is `Set-Content` in Windows PowerShell 5.1, `curl` is `Invoke-WebRequest`). A line the POSIX rules call read-only can write a file under PowerShell. So on Windows an incident escalates at its first command, and the server shows AI commands as "Not available" (ADR-0076).

Phase 11 brings Windows to the level of Linux. This ADR decides how a command runs on Windows, how it is classified, what the AI is told, and what changes on screen, with the same safety: rules decide, deny always wins, unknown is high impact, and the agent's opt-in stays the last word.

## Decision

### How a command runs

**Windows PowerShell 5.1, never `pwsh` or `cmd.exe`.** It ships with every supported Windows Server, while PowerShell 7 is an optional install, and the two differ in aliases and parsing (`sc`, `curl` and `wget` are aliases in 5.1 only, `&&` exists in 7 only). The rules below are written for one parser, so the agent runs that one: `powershell.exe` from the system directory found with `GetSystemDirectoryW`, as the script sensor does (ADR-0048), never one found on `PATH`. `cmd.exe` was rejected for the reasons of ADR-0047 and because it has no read-only cmdlets to build an allow-list on.

**The text classified is the text run.** The agent passes the line with `-EncodedCommand`, UTF-16LE in base64. Rust quotes arguments for `CreateProcess` and PowerShell splits its command line again, so passing the line as `-Command` text would add two layers that could change it. Around the line the agent adds a fixed prelude (`$ProgressPreference = 'SilentlyContinue'`, UTF-8 output without a byte order mark for PowerShell and for the programs it decodes) and epilogue (a program's exit code, else 1 when the line failed, else 0). The line is the last thing PowerShell parses before the epilogue, and a line that does not parse runs nothing. The agent still refuses a line with a newline, carriage return or NUL.

**The same process rules as the script sensor**, now shared in `monitorflow_sensors::powershell`: options `-NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass` (the server decided what runs, and a Group Policy execution policy still wins), the system variables only with `PATH` set to the system directories (`PSModulePath` included: without it each run searches every module for 18 to 33 s), from the root of the system drive, without a window, stdin closed, and inside a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The job is terminated at the timeout and after every run, so nothing the command started outlives it, the counterpart of the process group killed on Linux. Timeouts (`[remediation] command_timeout`, at most an hour) and output limits (the last 64 KiB of stdout and of stderr, kept while reading) are the ones of Linux.

**As the agent's own account, `NT SERVICE\MonitorFlowAgent`.** On Linux commands run as the unprivileged `monitorflow` user; this is its Windows counterpart (ADR-0047). LocalSystem was rejected: the only part of MonitorFlow that runs as LocalSystem, the update service, takes typed requests and builds its calls itself (ADR-0049). Sending it arbitrary PowerShell would be the general elevation path ADR-0036 and ADR-0047 ruled out, and it would hand full control of the host to whatever an approver let through, or to a bug in these rules. The account reads what diagnosis needs: services, processes, the System and Application event logs, CIM classes, volumes, counters, network state, and logs it may read. Changes such as `Restart-Service` need rights an administrator grants per service, as `systemctl restart` needs on Linux; without them the command fails with "access denied" and the AI escalates. The prompt tells the AI so.

**Turning it on.** The opt-in is `commands.shell`, as on Linux. Windows has no installer to run again with `MF_ALLOW_COMMANDS=1`, so the agent sets it itself: `monitorflow-agent.exe ai-commands on` (or `off`) writes `[commands] shell` into `agent.toml`, keeping every other line and comment (`toml_edit`), only when the result still loads, in place so the file keeps its access list. Then `Restart-Service MonitorFlowAgent`. Both lines are what the interface shows. The file is the right place because the MSI keeps it across upgrades. A service environment variable in the registry, the counterpart of the systemd drop-in, would be deleted with the service on every major upgrade, turning commands off without a word. An MSI property was not added: it would be a second way to say the same thing, and it would not reach agents already installed.

**What the agent reports.** `ShellHandler` is registered on Windows as on Linux, so `Hello` says `ACCEPTED` or `DISABLED` from the same `commands.shell` (ADR-0076). Agents from before this ADR keep reporting `UNSUPPORTED`. On a Windows server the interface now reads that as "its agent is too old for AI commands on Windows. It updates by itself", and the API's refusal says the same.

### How a command is classified

**By the rules of the server's shell.** `risk::classify_for(Shell, command, rules)` takes the shell from the server's `os_family`: `windows` is `Shell::PowerShell`, anything else `Shell::Posix`, which is `classify` as before. The incident loop, the approval of an edited command and the approval list use the server's shell; `POST /api/remediation/classify` takes an optional `"shell": "powershell"`. The length checks are shared. The PowerShell rules (`risk::powershell`) then follow the same steps as ADR-0041, written for PowerShell's syntax:

1. **Deny patterns first**, administrator ones then built-in ones, matched leniently on fragments of the command: lower case (PowerShell ignores case), backticks and carets removed (its and `cmd.exe`'s escapes), typographic dashes and quotes made ASCII (PowerShell reads `–` as `-`), `$env:SystemRoot`, `%windir%` and the other system directory variables replaced by their usual value, cut at every operator, with quoted strings both kept whole and split, and program names matched at any position, so `cmd /c "rd /s C:\Windows"` is found. Administrator deny patterns are matched without regard to case.
2. **Non-ASCII or control characters**: high.
3. **A strict lexer** that accepts only a pipeline of simple commands in argument mode: words, `-Parameter` tokens and single- or double-quoted strings. It refuses `;`, `&`, `&&`, `||` and newlines (`syntax.command_list`); `$` anywhere outside single quotes (`syntax.substitution`); backticks (`syntax.escape`); `(`, `)`, `{`, `}` and `@` (`syntax.grouping`: subexpressions, script blocks, arrays, hashtables, splatting, here-strings); `[` and `]` (`syntax.type`: type literals such as `[IO.File]::Delete`); `<` and `>` (`syntax.redirection`); `#` (`syntax.comment`); `--%` (`syntax.stop_parsing`); unterminated strings; and a quoted string joined to other text (`a'b'`), which PowerShell may split into two arguments (`syntax.quoting`).
4. **Every stage starts with a plain command name**, letters, digits, `.`, `_` and `-`: not a path, a quoted string, `.` or `&`. Names are lower-cased and the built-in aliases these rules know resolved (`gsv`, `gci`, `gc`, `select`, `where`, `ft`, ...). A name with `.exe` is the program, never an alias: `sc` is `Set-Content` and high impact, `sc.exe` the service tool. The first stage goes through the built-in rules, every later one must be a read-only filter.

**Parameters by full name.** PowerShell accepts any unambiguous prefix of a parameter name. The rules match parameters by their full name or a listed alias, and a prefix they do not list makes the command unknown, so the rules never guess what a prefix expands to. Parameters that must not appear are refused by prefix instead: `-Comp`, `-C` and `-cn` all count as `-ComputerName`. Positional arguments are checked as PowerShell binds them: to the first positional parameter not given by name, so the path checked is the one read, and one left over makes the command unknown. A word starting with `-` that is neither a number nor a parameter the rules read (`--name`, `--`) makes it unknown too.

**Read-only** (`readonly.*`):

- Cmdlets that only report, with any parameter but those that reach another computer or account, wait, never end, read arbitrary files or raise privileges (`-ComputerName`, `-Cluster`, `-CimSession`, `-Session`, `-Credential`, `-Wait`, `-Continuous`, `-AsJob`, `-Path`, `-LogPath`, `-EnableAllPrivileges`, ...): `Get-Service`, `Get-Process`, `Get-CimInstance`, `Get-WmiObject`, `Get-WinEvent`, `Get-EventLog`, `Get-Counter`, `Get-Volume`, `Get-Disk`, `Get-PSDrive`, `Get-HotFix`, `Get-ComputerInfo`, the `Get-Net*` and `Get-Dns*` cmdlets, `Get-ScheduledTask`, `Get-SmbShare`, `Get-WindowsFeature`, `Get-MpComputerStatus`, the IIS cmdlets `Get-IISSite`, `Get-IISAppPool`, `Get-Website`, `Get-WebAppPoolState`, and a few more. Any argument holding `\\` (another computer, a share) makes a command unknown.
- `Get-ChildItem` and `Get-Item` of absolute paths on a local drive, like `ls` of absolute paths; provider paths (`Env:`, `HKLM:`, `Cert:`), `~`, `.` and `..`, alternate data streams and short names are not paths here.
- `Get-Content` and `Select-String -Path` of files under `C:\Windows\Logs`, `C:\Windows\System32\LogFiles` or `C:\inetpub\logs` (on any drive), with the directory part written out and wildcards only after it, `-Tail` and `-TotalCount` as numbers, and no `-Wait` or `-Stream`.
- Programs with the arguments that only report: `hostname`, `whoami`, `ipconfig` (`/all`, `/displaydns`), `systeminfo`, `tasklist` (not `/s`, `/u`, `/p`), `netstat` (no interval), `sc.exe query|queryex|qc|q*`, `wevtutil el|gl|gli|qe` (`/c`, `/rd`, `/f`, `/q`, `/e` only), `w32tm /query`, `driverquery`.
- Filters after a pipe, with their parameters listed: `Select-Object`, `Sort-Object`, `Where-Object` in its simplified form only (`Where-Object Status -eq Running`: a property, an operator, a value; a script block is refused by the lexer), `Format-Table`, `Format-List`, `Format-Wide`, `Out-String`, `Measure-Object`, `Select-String` without `-Path`, `Group-Object`, `ConvertTo-Json`, `ConvertTo-Csv`. `ForEach-Object` is not one: `ForEach-Object Kill` calls a method on each process.

**Low impact** (`low.*`): `Start-Service` and `Restart-Service` of named services without `-Force`, unless a name has a wildcard (high, `high.service_pattern`) or names a service that keeps the host reachable, secure or monitored (high, `high.critical_service`: RPC, DCOM, the event log, WinRM, Remote Desktop, SMB, DHCP and DNS clients, network location, the firewall and its filtering engine, Defender, Netlogon, Kerberos, AD DS, DNS server, WMI, MonitorFlow's own services, ...); `Restart-WebAppPool`, `Start-WebAppPool` and `Start-Website` of one named pool or site; `Clear-DnsClientCache` and `ipconfig /flushdns`. These are the Windows counterparts of `systemctl restart` and of clearing a cache. The `cache_dir` rule stays Linux only: its paths and its `find -delete` form are POSIX.

**High impact, decided** (so an administrator allow rule never lowers them): cmdlets whose verb changes something (`Set`, `New`, `Remove`, `Stop`, `Start`, `Restart`, `Invoke`, `Install`, `Enable`, `Disable`, `Import`, `Export`, `Clear`, `Update`, `Write`, `Wait`, ...) unless a low-impact rule above applies; interpreters and launchers (`powershell`, `pwsh`, `cmd`, `wscript`, `mshta`, `rundll32`, `Invoke-Expression`/`iex`, `Start-Process`, `ForEach-Object`, `schtasks`, `wmic`, `msiexec`, ...); programs and aliases that change files, services, accounts, the network, disks or boot (`sc`, `net`, `netsh`, `reg`, `icacls`, `bcdedit`, `del`, `rm`, `curl`, `wget`, `Out-File`, `Tee-Object`, ...); `Stop-Process`, `kill`, `taskkill`; and `Restart-Computer`, `Stop-Computer`, `shutdown`, `logoff` (`high.power`), so a restart of the host always waits for an administrator. Everything else is `default.unknown`, high.

**Forbidden, built in.** Never run, and the incident escalates without running anything, as on Linux:

| Rule | What it catches |
| --- | --- |
| `forbidden.format` | `Format-Volume`, `Clear-Disk`, `Initialize-Disk`, `Remove-Partition`, `format`, `diskpart`, anything naming `\\.\PhysicalDrive` |
| `forbidden.system_files` | `Remove-Item` and its aliases, `del`, `rd`, `icacls`, `takeown`, `Set-Acl` on a drive root, `Windows`, `Program Files`, `ProgramData`, `Users`, `Boot`, or anything inside `Windows\System32`, `SysWOW64`, `WinSxS` or `Boot`: written with either slash, relative to `C:\` where commands run, through system directory variables, with wildcards or 8.3 short names that could match one, or with `..` |
| `forbidden.defender` | `Set-`, `Add-` and `Remove-MpPreference`; the `DisableAntiSpyware` family of policy values; stopping, pausing, reconfiguring or deleting Defender or firewall services or `MsMpEng`, also across a pipe (`Get-Service WinDefend \| Stop-Service`); `Set-NetFirewallProfile -Enabled`; `netsh advfirewall ... off`; removing the Defender feature |
| `forbidden.accounts` | Local and Active Directory user and group changes (`New-LocalUser`, `Add-LocalGroupMember`, `Set-ADAccountPassword`, ...), `net user`, `net localgroup` or `net group` with arguments, `cmdkey`, `ntdsutil`, saving the SAM, SECURITY or SYSTEM hives, dumping `lsass` |
| `forbidden.recovery` | Deleting shadow copies (`vssadmin`, `wmic shadowcopy`, `Win32_ShadowCopy` removed through CIM or WMI) or backups (`wbadmin delete`), `bcdedit /set` and `/delete`, `reagentc /disable`, `Disable-ComputerRestore` |
| `forbidden.event_logs` | `Clear-EventLog`, `Remove-EventLog`, `Limit-EventLog`, `wevtutil cl`, turning a log off with `wevtutil sl /e:false`: they destroy the evidence |
| `forbidden.encoded` | `powershell -EncodedCommand` and its abbreviations, `FromBase64String`: what they run cannot be checked |

`Restart-Computer` is not forbidden: it is high impact, so it runs only once an administrator approves it, as `reboot` on Linux.

**Administrator rules** apply to both shells, as rules are stored per customer and site, not per system. Deny patterns are matched without regard to case on Windows. Allow rules apply, as on Linux, only to commands the built-in rules did not decide, after every syntax rule. Creating a rule is not refused for naming a program that is reserved on Windows only: `net` or `curl` mean something else on a Linux server, and on Windows the built-in rules decide them before any allow rule is read.

### What the AI is told

`prompt::system` takes the shell. On Windows it says the server is Windows, that commands run in Windows PowerShell 5.1 as `NT SERVICE\MonitorFlowAgent`, not an administrator, from `C:\` with the system `PATH`, and are killed with everything they started at the timeout; that Unix commands and `/var/log` do not exist; which constructs are refused (statements, redirections, `$`, parentheses and script blocks, `@`, brackets, backticks, other computers, anything that runs other code), which filters a pipe may use, to write full parameter names and `sc.exe` rather than `sc`; and which commands diagnose (`Get-Service`, `Get-Process`, `Get-CimInstance Win32_LogicalDisk`, `Get-WinEvent -LogName System -MaxEvents 50`, `Get-Counter`, `Get-NetTCPConnection`, `Get-Content -Tail` of the log directories, the IIS cmdlets) and which changes wait for approval and may lack rights. A test classifies the prompt's own examples, so the prompt cannot suggest what its rules refuse. The Linux prompt is unchanged.

### Snapshots before changes

Unchanged, and the same on both systems: the snapshot hook (ADR-0046) runs before every change and snapshots servers mapped to a Proxmox VM (ADR-0044), Windows VMs included. Any other Windows server records `method: "none"`, rollback is limited, and the approval page says so in the same words as for Linux ("No snapshot before this change: the server is not mapped to a Proxmox VM."). Hyper-V, VMware and Volume Shadow Copy restore points were not added: a Windows-only snapshot path would be a second mechanism to configure for what the Proxmox mapping already covers, and a VSS copy does not roll back a service's configuration.

### On screen and in the API

- The approval page states what runs the command: "Runs in Windows PowerShell, as the agent's account." or "Runs with /bin/sh, as the agent's user.", from the new `shell` field of each pending command.
- A Windows server whose AI commands are off shows the two PowerShell lines, for an elevated PowerShell, on its Commands tab; Administration › AI shows the Linux and the Windows line. A refusal from the API names `ai-commands on` for Windows and `MF_ALLOW_COMMANDS=1` for Linux.
- "Not available" now only means an agent too old for AI commands, which updates by itself.

## Consequences

- Windows servers run the same remediation loop as Linux ones, with rules of their own and the same tiers, approvals, audit trail, limits, snapshots and opt-in.
- The rules refuse far more PowerShell than they understand: `$PSVersionTable`, `-FilterHashtable @{...}`, `Where-Object { ... }`, `2>$null` and calculated properties are all high impact. The prompt steers the AI to forms the rules accept.
- Classification follows `servers.os_family`. A server whose agent never reported a family is classified as Linux, and a Windows agent always reports `windows` (ADR-0047).
- Approvers read PowerShell; the approval page names the shell, and an edited command is classified by the same rules.
- Most changes need rights the agent's account does not have by default. Granting it the right to restart one service (with `sc.exe sdset` and the account's service SID) is an administrator's decision per service, outside MonitorFlow, as are sudo or polkit rules on Linux.
- Each command starts a Windows PowerShell process: about a second before the command itself.
- Follow-ups: PowerShell 7 if it becomes the norm on Windows Server, which needs its own parser rules; a Windows `cache_dir` rule; per-system administrator rules if rules for one system get in the way on the other.
