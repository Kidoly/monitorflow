# ADR-0183: Ready-made application checks

Date: 2026-11-24
Status: accepted; extends ADR-0148 (checks from a probe), ADR-0150 (sealed check passwords) and ADR-0146 (what the importer moves). Completed on 2026-11-25 with SQL Server, and with cloud accounts (AWS and Azure), which reuse the inventory of ADR-0156, and on 2026-11-26 with Kubernetes clusters

## Context

MonitorFlow watched databases and containers from the outside only: a service running, a port answering. A PostgreSQL that accepts connections but has run out of them, a replica three hours behind, a Redis evicting keys because it is full, a container restarting every minute: none of it showed without a script. Tools people move from have these as built-in sensors or templates (PRTG's database and Docker sensors, Zabbix's "PostgreSQL by Zabbix agent 2" and its siblings, Prometheus exporters), and the roadmap asks for PostgreSQL, MySQL and MariaDB, SQL Server, Redis, Java (JMX), Docker, Kubernetes and the main cloud providers as check templates instead of scripts.

That list is several projects. This decision delivers the databases people run most (SQL Server since 2026-11-25), Redis and Docker end to end, and records how the rest will follow. Java (JMX) followed on 2026-11-25, in its own section below.

What exists to build on: check kinds built by name on agents and probes (ADR-0012, ADR-0148), a password sealed per check row and given only to whoever runs it (`sensor_configs.secret`, ADR-0150, ADR-0125), the agent's `sensors.port_targets` limits (ADR-0111), and thresholds that apply to every instance of a metric (ADR-0017).

## Decision

### New kinds, in a crate of their own

`monitorflow-apps` (`crates/apps`) holds the kinds `postgresql`, `mysql` (MySQL and MariaDB), `mssql` (SQL Server), `redis` and `docker`, and, since 2026-11-25, `jmx` (its own section below). They speak the applications' own protocols, so they stay out of `monitorflow-sensors`, which has no transport code (ADR-0021). The PostgreSQL and MySQL clients are sqlx's, already in the workspace, over rustls; Redis is a bounded subset of its protocol (RESP2: `AUTH`, `INFO`) written here, about a hundred lines; SQL Server is a bounded subset of TDS 7.4 written here too (below); Docker is HTTP/1.0 `GET` over the engine's Unix socket, with bodies bounded to 16 MiB. A collection connects, reads, and closes: no connection is kept between collections, so a restarted server is just the next collection.

Every kind writes `up` (1 when the application answered and the login worked; 0 with labels `reason`, one of `connect`, `timeout`, `tls`, `login`, `permission`, `protocol`, and `error`) and `response_seconds`, then its own metrics. A failure is a sample, not a sensor error, so a stopped database alerts like a failed website check. Counters are turned into what changed since the last collection (deadlocks, slow queries, evictions, restarts) or a rate per second, and hit ratios are computed over the interval, not since the server started, so a cache that just went cold shows.

| Kind | What it reads | Main metrics |
| --- | --- | --- |
| `postgresql` (10 or later) | `pg_stat_activity`, `pg_locks`, `pg_stat_database`, `pg_database_size`, `pg_stat_replication`, `pg_stat_wal_receiver` | connections against `max_connections`, active and idle in transaction, slow queries (running longer than `slow_after`, 30 s), longest query and transaction, waiting locks, deadlocks, cache hit ratio, transactions per second, size per database, replicas and their lag in bytes and seconds, and on a standby whether it streams and how old what it replayed is |
| `mysql` (MySQL 5.7, MariaDB 10.3 or later) | `SHOW GLOBAL STATUS`, `SHOW GLOBAL VARIABLES`, `SHOW REPLICA STATUS` (or `SLAVE`), `information_schema.tables` every 10 minutes | connections against `max_connections`, threads running, queries per second, slow queries, aborted connections, InnoDB buffer pool hit ratio, row lock waits, size per schema, replica I/O and SQL threads and `Seconds_Behind_Source` |
| `mssql` (SQL Server 2012 or later, on Windows or Linux) | `sys.dm_os_performance_counters`, `sys.configurations`, `sys.dm_exec_requests`, and with Always On `sys.dm_hadr_availability_replica_states`, `sys.dm_hadr_database_replica_states` and `sys.availability_groups_cluster` | user connections against `user connections`, batch requests per second, page life expectancy, buffer cache hit ratio, processes blocked and the longest blocked wait, longest request, lock waits per second, deadlocks, data, log and log use per database, each availability replica's connection and health, and per database on a secondary its send and redo queues and lag (2016 or later) |
| `redis` (5 or later, Valkey, KeyDB) | `INFO` | clients, blocked clients, rejected connections, memory against `maxmemory`, fragmentation, evicted keys, keyspace hit ratio, keys, last snapshot and AOF write, replicas and their lag, and on a replica its link to the primary |
| `docker` (Docker or Podman) | `/version`, `/containers/json`, each container's inspection and one-shot statistics | per container: running, restarts (total and since the last collection), health check, processor share and memory against its limit; containers running and stopped |
| `jmx` (any JVM with the Jolokia agent) | `java.lang` MBeans (`Memory`, `GarbageCollector`, `Threading`, `Runtime`, `OperatingSystem`), then Tomcat's (`ThreadPool`, `GlobalRequestProcessor`, `Manager`) and a Kafka broker's (`ReplicaManager`, `KafkaController`, `BrokerTopicMetrics`, `KafkaRequestHandlerPool`) where they exist | heap and non-heap against their maximum, collections and time per collector and the share of time collecting, threads and deadlocked threads, processor share, file descriptors, uptime; Tomcat's busy threads against `maxThreads`, requests, errors, time per request and sessions; Kafka's under-replicated, under-min-ISR and offline partitions, active controller, ISR shrinks, messages and bytes per second, request handler idle share |

The exact list, units and descriptions are in `monitorflow_apps::templates`, which the API serves (below), so the code, the API and the guides cannot drift apart.

### Where each runs

**Databases and Redis run where a port check runs.** By default on the server's agent, against `127.0.0.1`, which works with the out-of-the-box configuration of all of them (PostgreSQL, MySQL and Redis listen on the loopback only; SQL Server on every address, on Linux and on Windows when TCP is on). SQL Server runs from the agent on Windows as on Linux. An agent with `sensors.port_targets` connects only where that list allows, and a host name must be listed itself, since the clients resolve names on their own. From the form, or with `probe` in the API, the check runs instead from the central server or a relay of the site (ADR-0148), against the server's address, which is how a device or a managed database without an agent is watched. The central server never connects to a link-local address, as for website checks: an operator of one customer must not reach the instance metadata of the machine serving all of them.

**Docker runs on the server's agent only**, on Linux. Its API is a Unix socket, and a probe reaching a remote engine would need its TCP API opened, with root's power to whoever holds the certificate. The server never names a socket path: `engine` is `docker` (`/var/run/docker.sock`) or `podman` (`/run/podman/podman.sock`).

**Watched containers** are those that run, and stopped ones whose restart policy is `always` or `unless-stopped`: those meant to run. A one-off container that exited is not an incident. `containers` narrows them with a regular expression on names. At most 200 containers are looked at.

### Credentials

**The password is the check's own, sealed** in `sensor_configs.secret` like a website check's (ADR-0150), the column now documented for both. The API takes it as the parameter `password`, never stores it in `params`, never returns it (rows say `secret_set`), never writes it in the audit log (which records parameter names only), and gives it only to the agent or probe that runs the check, over their mTLS stream. An update without `password` keeps it, but only while the kind, `host` and `port` stay the same: a kept password never goes to a new address. Errors are scrubbed of it before they become the `error` label.

**A read-only account is recommended, with the least rights**, as the guides say step by step:

| Application | Account |
| --- | --- |
| PostgreSQL | `CREATE ROLE monitorflow LOGIN PASSWORD '...'; GRANT pg_monitor TO monitorflow;`. Without `pg_monitor`, PostgreSQL hides other roles' sessions and replication, and the numbers cover less |
| MySQL, MariaDB | `CREATE USER 'monitorflow'@'host' IDENTIFIED BY '...'; GRANT PROCESS, REPLICATION CLIENT ON *.* TO 'monitorflow'@'host';`. Schema sizes cover the schemas it can see. Without `REPLICATION CLIENT`, replication is left out rather than the check failing |
| Redis | `ACL SETUSER monitorflow on >... -@all +info +ping` (Redis 6), or the `requirepass` password without a user |
| SQL Server | `CREATE LOGIN monitorflow WITH PASSWORD = '...'; GRANT VIEW SERVER STATE TO monitorflow;`, or `VIEW SERVER PERFORMANCE STATE` from SQL Server 2022, which is enough for every view read (checked against 2022 with an availability group). No user in any database. SQL Server authentication must be on; Windows sign-in is not supported yet |
| Docker | No account: the agent's user joins the `docker` group (`usermod -aG docker monitorflow`, then restart the agent). That group equals root on the machine, so it is a deliberate step on the server, like Hyper-V's (ADR-0156), written in the guide and in the check's error. The check only reads |

Encryption: `tls` is `prefer` by default for PostgreSQL and MySQL (encrypted when the server offers it, its certificate not verified, what their own clients do by default), `verify` (certificate and name verified against the machine's roots) or `off`. PostgreSQL's SCRAM and MySQL's `caching_sha2_password` never send the password in clear over `prefer`. MySQL 8 without encryption needs an RSA exchange for `caching_sha2_password`, which is not built in (its RSA crate has an open timing advisory); the guide says to keep encryption on. Encrypted Redis is not checked yet: `tls` takes `off` only.

SQL Server: `prefer` asks for an encrypted session (`ENCRYPT_ON`) and accepts the server's certificate unverified, what its clients do with `TrustServerCertificate`, since SQL Server makes a self-signed X.509 version 1 certificate at start when it has none, which WebPKI does not even parse (so the handshake's signatures are not checked either: under a certificate nobody vouches for they prove nothing). `verify` checks the certificate and name against the machine's roots. Unlike PostgreSQL and MySQL, a TDS login carries the password only obfuscated, so `prefer` never falls back to clear text: a server that offers no encryption fails the check with `tls`, and only `off` (`ENCRYPT_NOT_SUP`) sends it in clear. The mode that encrypts the login only (`ENCRYPT_OFF`) is never asked for. TDS 8.0's strict encryption (TLS before the pre-login, SQL Server 2022 with `Force Strict Encryption`) is not supported yet.

### SQL Server's protocol, written here

`tiberius`, the Rust TDS client, builds its rustls backend on aws-lc-rs hard-coded, a second cryptography library next to the workspace's ring, with its native build on every agent target; its native-tls backend means OpenSSL or SChannel. The check needs little of TDS: the pre-login and its encryption, with the TLS handshake carried inside pre-login packets, a SQL Server login (LOGIN7), one `SELECT` per batch, and the token stream back (column metadata, rows, null-bitmap rows, errors, information, login acknowledgement, environment changes, done). `crates/apps/src/tds.rs` does that in about 900 lines, comments included, on tokio-rustls and ring, reading only the column types its own queries return (integers, floats, decimals, bounded text: every query casts its columns) and refusing anything else as `protocol`; a message is bounded to 4 MiB and 5,000 rows. Server errors keep their number, which says `login` (18456 and its siblings) from `permission` (300, 297, 229 and siblings).

### Templates: the check and its alerts

A template is the check and the alerts that come with it. `GET /api/check-templates` lists, per kind, who runs it, its parameters with their defaults, its metrics and its default alerts. `POST .../sensor_configs` takes `"default_alerts": true` on a create to add them, in the same transaction, as ordinary thresholds named after the check (`monitorflow_<check>_<suffix>`), on the server or site of the row, where none exists on that metric for every instance. They are then changed, silenced or removed like any threshold, and every richer rule of ADR-0153 applies to these metrics. The web form's switch "Add the recommended alerts" sends it.

| Kind | Default alerts |
| --- | --- |
| `postgresql` | not answering (`up < 1`, 2 min, critical); connections over 80% warning, 95% critical (5 min); a transaction open for more than an hour (warning, 5 min); more than 10 locks waited for (warning, 5 min); a deadlock (warning); cache hit ratio under 90% (warning, 30 min); a replica more than 1 GiB behind (warning, 10 min); a standby not streaming (critical, 5 min); a standby more than 5 minutes behind (warning) or 30 (critical) |
| `mysql` | not answering (critical, 2 min); connections over 80% or 95%; more than 10 slow queries a collection (warning, 5 min); buffer pool hit ratio under 95% (warning, 30 min); more than 10 lock waits (warning, 5 min); replica I/O or SQL thread stopped (critical, 2 min); replica behind by 5 or 30 minutes |
| `mssql` | not answering (critical, 2 min); connections over 80% or 95% (5 min); page life expectancy under 300 s (warning, 15 min); buffer cache hit ratio under 95% (warning, 30 min); a process blocked (warning, 5 min); a deadlock (warning); a log over 80% or 95% full (5 min); an availability replica disconnected (critical, 2 min) or not healthy (critical, 5 min); a secondary's send queue over 1 GiB (warning, 10 min) or its lag over 5 or 30 minutes |
| `redis` | not answering (critical, 2 min); memory over 80% or 95% of `maxmemory` (5 min); keys evicted for 15 minutes (warning); a connection rejected (warning); a failed snapshot or AOF write (critical); a replica's link to its primary down (critical, 2 min) |
| `docker` | the engine not answering (critical, 2 min); a container not running (critical, 2 min); a container restarted (warning); a container unhealthy (critical, 2 min); a container over 90% of its memory limit (warning, 5 min) |
| `jmx` | Jolokia not answering (critical, 2 min); heap over 90% warning, 95% critical (10 min); more than 10% of the time collecting garbage warning, 25% critical (10 min); a deadlocked thread (critical, at once); file descriptors over 80% or 95% (5 min); a Tomcat connector over 90% of `maxThreads` (warning, 5 min); an under-replicated Kafka partition (warning, 5 min); a partition under `min.insync.replicas` or offline (critical, 2 min); Kafka's request handlers less than 20% idle (warning, 10 min) |

Alerts on metrics a server never writes (replication on a lone server) never fire. One threshold covers every instance (every database, replica, container), so one restarting container is one incident naming it.

### Kubernetes: a cluster as a device

Added after the first four kinds, as the fifth of this crate (cloud accounts, below, have a crate of their own).

**A cluster is a device** (ADR-0148): its name, the address of its API server, the central server or the relay of the site that checks it. Its check is of kind `kubernetes`, run by probes only: agents refuse it, as they refuse `vmware`, since a cluster is not a machine with an agent, and its API is what describes it. One check reads the whole cluster each collection. Its incidents are those of the device, so thresholds, silences, notifications and dashboards apply unchanged, as for a vCenter (ADR-0156).

**The REST API over HTTPS, read only.** A collection makes `GET` requests only, with `Authorization: Bearer` and the service account's token, through reqwest over rustls: `/version`, then `/api/v1/nodes`, `/api/v1/pods`, `/apis/apps/v1/deployments`, `statefulsets` and `daemonsets`, and `/api/v1/persistentvolumeclaims`, for all namespaces, each list read page by page (`limit=500` and its `continue` token). It stops at 10,000 objects of one list and 64 MiB in all, with an error that says to narrow `namespaces`; no redirect is followed and no proxy used. No connection is kept between collections, as for the other kinds. A watch (`?watch=1`) was not chosen: it would hold a stream per cluster on every probe, and a collection a minute is the resolution of every other check.

**The token and the CA are sealed together.** The check's parameters `token` and `ca_certificate` are taken out of `params` by the API and sealed as one JSON object in `sensor_configs.secret` (ADR-0125, ADR-0150), never returned (rows say `secret_set`), never written in the audit log, and given only to the probe that runs the check, which gets them back as two parameters over its mTLS stream. The CA is public data, but sealing it with the token keeps the pair whole: the token never goes to a server the CA does not vouch for. An update without `token` keeps both; one with it replaces both, so a CA left out then means the machine's roots; `ca_certificate` alone is refused. A kept token never follows the check to a new `host` or `port`, as a kept password does not. Errors are scrubbed of the token.

**The certificate is always verified**, against the cluster's CA when one is given (PEM, possibly pasted on one line, or a kubeconfig's `certificate-authority-data`, the base64 of the PEM), else the machine's roots, as some managed clusters' API certificates are publicly trusted. The address must be one the certificate names. There is no option to skip it: the token would go to whoever answers. Pinning a fingerprint, as for vCenter, was not needed: a cluster always has a CA, and it is in every kubeconfig.

**Least rights.** The guide and `deploy/kubernetes/monitorflow-reader.yaml` give a ServiceAccount `monitorflow-reader` in a namespace `monitorflow`, a ClusterRole of the same name with `get` and `list` on `nodes`, `pods` and `persistentvolumeclaims` (core) and on `deployments`, `statefulsets` and `daemonsets` (`apps`), its ClusterRoleBinding, and a `kubernetes.io/service-account-token` Secret for a token that does not expire (or `kubectl create token --duration` for one that does). It reads no secret, config map or log, and can neither exec into a pod nor change anything. `/version` is readable by any authenticated account (`system:public-info-viewer`). A 403 names the path refused and the ClusterRole to bind.

**What it measures.** Besides `up` (label `version`, the API server's `gitVersion`; 0 with `reason` among `connect`, `timeout`, `tls`, `login`, `permission`, `protocol`) and `response_seconds`:

| Object | Instance | Metrics |
| --- | --- | --- |
| Node | its name | `node_ready` (labels `roles`, `kubelet_version`), `node_memory_pressure`, `node_disk_pressure`, `node_pid_pressure`, `node_network_unavailable` (1 while the condition is true), `node_unschedulable` (cordoned); and `nodes`, `nodes_not_ready` for the cluster |
| Namespace | its name | `namespace_pods`, `namespace_pods_not_running` (label `pods`: the pods and why, `api-1 CrashLoopBackOff`, within 200 bytes), `namespace_pod_restarts` (container restarts since the last collection, a pod first seen after the first collection counting all its restarts), `namespace_claims_pending`, `namespace_claims_lost` (label `claims`); and `pods`, `pods_not_running`, `claims_pending` for the cluster |
| Deployment, stateful set, daemon set | `namespace/kind/name` | `workload_replicas_desired` (label `workload`), `workload_replicas_ready`, `workload_ready_ratio` (absent when scaled to zero); and `workloads_short` for the cluster |

Pods are counted per namespace, not one series per pod: pod names change with every rollout, which would make series without end and incidents that resolve by disappearing. The `pods` label still names the pods at fault in the incident. **A pod does not run** when it is `Pending`, `Unknown`, `Failed` (unless a Job owns it: that is the job's failure), or `Running` without its `Ready` condition; the reason is a waiting container's (`CrashLoopBackOff`, `ImagePullBackOff`) or else the phase. Pods being deleted and `Succeeded` ones are not counted. `namespaces`, a regular expression, narrows pods, workloads and claims; nodes are always the cluster's.

**Default alerts**: the API not answering (critical, 2 min); a node not ready (critical, 5 min); memory, disk or PID pressure (warning, 5 min); the network unavailable (critical, 5 min); pods not running in a namespace (warning, 10 min); a container restart (warning, at once, as for Docker); a workload under all its ready replicas (warning) or under half (critical), for 10 minutes; a claim pending for 10 minutes (warning); a claim lost (critical, at once).

**Tests.** A fake API server over TLS with a CA of its own (`crates/apps/src/kubernetes/tests.rs`) covers pages, namespaces, restarts, 401, 403, an untrusted certificate and a closed port. `scripts/kubernetes-test.sh` runs k3s in a container, applies the guide's manifest, checks with `kubectl auth can-i` what the account may and may not do, and runs `crates/apps/tests/real.rs` against it. It runs k3s without a pod network (`--flannel-backend=none`, no kube-proxy), since those need iptables modules a test machine may lack and the check reads only the API; its node is then not ready and its pods pending, which the test reads as such.

### Cloud accounts: AWS and Azure

**An AWS account or an Azure subscription is a device**, as a vCenter is (ADR-0156): `POST /api/devices` with `cloud` credentials, no address to type (it becomes the provider's API host) and no ping. Its check, of kind `aws` or `azure` from a crate of its own, `monitorflow-cloud`, runs every 5 minutes (120 s timeout) **on the central server only**: the store never sends a cloud check to a relay, the API refuses one with a relay as its probe, and relays are not built with the crate. A cloud account is reached over the Internet like the central server's own website checks, and keeping its secret on one machine is simpler than on every relay of a site.

**Its machines are the inventory of ADR-0156.** A collection writes each virtual machine as the shared `vm_*` samples and `vm_info` (`virt=vm`), so `virtual_objects`, the account's page, the server's "Virtual machine … of …" line, matching, "Not this one" and "Install the agent" work unchanged. The `key` is the instance ID (`i-…`) or Azure's VM ID; `host` is the availability zone or the region; `vm_info` adds `size` (instance type or VM size). The source's `up` carries `provider` (`aws`, `azure`), which the web interface uses to show the cloud columns. Snapshots are not written: clouds have none in this sense. Measures, per running machine:

| Measure | AWS | Azure |
| --- | --- | --- |
| `vm_powered_on`, `vm_cpu_count` | `instanceState`, `cpuOptions` | `PowerState/running` of the instance view |
| `vm_cpu_usage_ratio` | CloudWatch `CPUUtilization` (Average) | Azure Monitor `Percentage CPU` (Average) |
| `vm_network_in_bytes_per_second`, `vm_network_out_bytes_per_second` | `NetworkIn`, `NetworkOut` (Sum over 300 s) | `Network In Total`, `Network Out Total` (Total over PT5M) |
| `vm_disk_read_bytes_per_second`, `vm_disk_write_bytes_per_second` | `EBSReadBytes`, `EBSWriteBytes` | `Disk Read Bytes`, `Disk Write Bytes` |
| `vm_status_checks_failed`, `vm_status` | `DescribeInstanceStatus`: impaired system, instance and attached volume checks; `vm_status` 2 when one is impaired, 1 while they initialize or lack data | `VmAvailabilityMetric`: 1 failed when under 1 |

The newest point of the last 20 minutes is taken, as basic EC2 monitoring lags. Stopped machines get no metrics and no status checks. At most 2,000 machines per account and 30 regions. `up` is 0 with `reason` (`connect`, `login`, `permission`, `api`) and the provider's own message when any call failed, the machines read before the failure still written, so a missing CloudWatch right shows on the account instead of hiding its machines.

**Small HTTP clients instead of the SDKs.** AWS is three Query API calls (`ec2:DescribeInstances`, `ec2:DescribeInstanceStatus`, `cloudwatch:GetMetricData` with up to 500 queries a call), signed with Signature Version 4 written here on `ring`'s HMAC-SHA256 and SHA-256 (about a hundred lines, tested against vectors of the AWS test suite), answers read with the bounded XML reader of `monitorflow-vmware`. Azure is OAuth 2.0 client credentials against `login.microsoftonline.com` for a Resource Manager token, kept until a minute before it expires, then `GET`s of Resource Manager: virtual machines with `statusOnly=true` (their power state in one list), network interfaces (MAC and private addresses), and one Azure Monitor metrics request per running machine, eight at a time. A `nextLink` is followed only on Resource Manager's own host, so the token goes nowhere else. Every request is HTTPS (`https_only`), redirects are not followed, answers are bounded to 32 MiB, and no parameter names an endpoint: a stored check cannot be pointed at another host. Tests use fake APIs on the loopback through a constructor only tests reach.

**Credentials are the device's, sealed** in `cloud_credentials` (one row per device: `provider`, `settings` with what is not secret, and `secret` sealed as `cloud_credentials.secret`, ADR-0125), as vCenter credentials are. The API never returns the secret (`secret_set`), refuses credentials as check parameters, and audits `device.create`, `device.cloud_update` and `device.cloud_delete` without it. A change keeps the stored secret only while the provider and the identity stay the same (the access key ID, or the tenant and application): a kept secret never goes to another identity. The provider cannot change. The store adds the credentials to the check in memory on the central server; the sensor's `Debug` hides them, and errors are the provider's messages, which never quote them.

**Least rights**, as the guide says step by step:

| Provider | Credentials and rights |
| --- | --- |
| AWS | An IAM user's access key with a policy allowing only `ec2:DescribeInstances`, `ec2:DescribeInstanceStatus` and `cloudwatch:GetMetricData` on `*` (they take no resource) |
| Azure | A service principal (application ID and client secret) with the built-in Reader role on the subscription, or a custom role with `Microsoft.Compute/virtualMachines/read`, `Microsoft.Compute/virtualMachines/instanceView/read`, `Microsoft.Network/networkInterfaces/read` and `Microsoft.Insights/metrics/read` |

No call of either client changes anything in the account, and nothing runs on a monitored server, so no consent on a server is involved.

**Matching** is ADR-0156's, by the signals the agent already reports, not by a new one: Azure's VM ID is the SMBIOS UUID the guest reads (both byte orders are tried), so an Azure machine with the agent matches by its hardware ID; an EC2 instance's SMBIOS UUID is not its instance ID, so it matches by a network card's MAC address (EC2 lists them), then an address or its private DNS name, which is its default host name. Agents reporting their instance ID from the metadata service would make AWS matching exact; it is left for later, as it needs a network call from the agent.

**Default alerts**, as ordinary thresholds on the device: the account cannot be read (`monitorflow_<provider>_up < 1`, 10 minutes, critical) and a machine's status check failing (`monitorflow_<provider>_vm_status_checks_failed > 0`, 10 minutes, critical, one incident per machine).

**Costs.** CloudWatch bills `GetMetricData` per metric asked for: five per running instance every 5 minutes, about 43,200 a month per instance; status checks come from EC2 and cost nothing. The guide says so.

**The API**, under `/api/v1` with its OpenAPI document (tag `cloud`): `POST /api/devices` takes `cloud`, `POST /api/devices/cloud/test` signs in once from the central server and says how many machines it sees and whether metrics can be read, `GET`, `PUT` and `DELETE /api/devices/{id}/cloud`. Operators of the site add and change accounts; viewers read the inventory, as for vCenters.

### Moving from another tool

The importer (ADR-0146) maps the equivalent sensors to these kinds where it is simple, PRTG first: its PostgreSQL, MySQL, Microsoft SQL v2, WMI Microsoft SQL Server and Docker container sensors (a device with a WMI SQL Server sensor is a Windows machine the agent goes on), the Zabbix templates "PostgreSQL by Zabbix agent 2", "MySQL by Zabbix agent", "Redis by Zabbix agent 2", "Docker by Zabbix agent 2", "MSSQL by Zabbix agent 2" and their siblings, "MSSQL by ODBC" (the one ODBC template moved, as it reads the counters the check reads, from where the check connects), and Prometheus jobs scraping `postgres_exporter`, `mysqld_exporter` and `redis_exporter`, and jobs named after SQL Server (`mssql`, `sqlserver`), as its exporters' ports are any service's. Passwords are never exported by these tools, so a database check is approximated: "enter the password on the check". A PRTG database sensor's own SQL query is not run: its connection and response time are, with the template's metrics. The Java check's mappings are in its section.

For Kubernetes, PRTG has no sensor of its own: people read a cluster with REST Custom or HTTP Advanced sensors on its API, or with script sensors. A REST Custom or HTTP sensor whose URL is the API (a path under `/api/v1/` or `/apis/`, or `/healthz`, `/livez`, `/readyz` or `/version` on port 6443) and a sensor whose type names Kubernetes become the device's `kubernetes` check, at the URL's address; a REST Custom sensor on anything else is not moved. Zabbix's "Kubernetes ... by HTTP" templates become one `kubernetes` check per host, at `{$KUBE.API.URL}` (or `{$KUBE.API.ENDPOINT.URL}`, `{$KUBE.API.SERVER.URL}`), their items and triggers covered. Prometheus jobs scraping an API server (named `apiserver`, as `kubernetes-apiservers` is, or on port 6443) become the check of that address. A cluster is always checked from a probe, at the server's address when the host has an agent. The token is never exported: "enter the service account's token and the cluster's CA on the check".

### What comes next, each in its own task

- **SQL Server, what is left**: signing in with a Windows account (NTLM or Kerberos through SSPI on the Windows agent), TDS 8.0's strict encryption, and finding a named instance's port through SQL Server Browser.
- **Java (JMX)**: delivered, see its section below.
- **Kubernetes** is now decided above. Left for later: an inventory of the cluster's objects shown on the device's page, as VMware's (`_info` samples into `virtual_objects`, ADR-0156), and nodes matched to the servers already monitored; jobs and cron jobs that failed; and the resource use of pods and nodes, which needs metrics-server (`metrics.k8s.io`).
- **Google Cloud**, a third cloud account kind, `gcp`, on the model above: a service account's JSON key sealed per device, an OAuth token from a JWT signed with RS256 on `ring` (`RsaKeyPair::from_pkcs8`), Compute Engine's `instances.aggregatedList` for the machines (a GCP MAC address is `42:01` followed by the internal IPv4 address, which agents report), and Cloud Monitoring's `timeSeries.list` once per metric for the whole project (processor utilization, network and disk bytes, uptime), with the roles Compute Viewer and Monitoring Viewer. Left out of the first change to keep it reviewable.
- **Managed databases** (RDS, Azure SQL, Cloud SQL) then reuse the database kinds above for what is inside, and the cloud check for what the provider sees. AWS accounts reached by assuming a role (`sts:AssumeRole`) rather than with a user's key, and agents reporting their EC2 instance ID for exact matching, come with them.
- **Jolokia with a pinned certificate**: Jolokia's HTTPS certificates are often self-signed; accepting one by its SHA-256 fingerprint, as vCenter's are (ADR-0156), would let a probe send the password without a certificate the machine trusts.
- **Encrypted Redis** and an **agent-local Unix socket** for PostgreSQL and MySQL (peer authentication without a password).

### Java (JMX) through Jolokia (2026-11-25)

JMX's own transport is Java RMI, which only a JVM speaks well, so a Rust agent cannot read it directly. **The `jmx` kind reads Jolokia**, the open source HTTP and JSON bridge to JMX, loaded into the JVM as a Java agent (one JAR and one `-javaagent` option; Tomcat can run it as a web application). It is what the Zabbix Java gateway does as a separate process, without the process. A JVM without Jolokia is not read: the guide shows how to add it, and the importer says so where it maps a Zabbix JMX template.

**One `POST` per collection**, a Jolokia bulk request of about twenty reads over reqwest on rustls, the answer bounded to 4 MiB, without proxy, redirects or a kept connection. Each read answers on its own, so a missing MBean (no Tomcat in a Kafka broker) or one a Jolokia policy refuses leaves its metrics out without failing the others; `up` is 0 only when the heap itself cannot be read, which every JVM has. Multi-attribute reads ask `ignoreErrors`, so an attribute this JVM lacks (file descriptors on Windows) is left out. Instances (collectors, connectors, web applications) are capped at 50 per pattern.

**Groups**: Tomcat (domains `Catalina` and `Tomcat`, the second for Spring Boot) and Kafka are read by default, as reading an absent MBean costs one line of the answer; `groups` narrows it (`tomcat`, `kafka`, `none`). One check reads one JVM.

**Where it runs**: like the databases, on the server's agent against `127.0.0.1:8778` (Jolokia's default, listening on the loopback) or from a probe against the server's or device's address, within `sensors.port_targets` and never to a link-local address from the central server.

**Credentials and encryption**: Jolokia's HTTP Basic user and password, the password sealed per check as above. `tls` is `off` (HTTP, the default, as Jolokia is plain HTTP out of the box) or `verify` (HTTPS, certificate and name verified against the machine's roots); there is no `prefer`, which over HTTP would mean an unverified certificate. **A password goes over HTTPS only, or to the loopback** (`127.0.0.0/8`, `::1`, `localhost`): Basic authentication sends it with every request, readable by anyone between a probe and the JVM over plain HTTP. The server refuses such a row as the agent would.

**Read-only**: the check sends `read` requests and one `exec`, `findDeadlockedThreads`, the only way JMX gives deadlocked threads. The guide recommends a Jolokia policy allowing `read` only; deadlocked threads are then absent, said in the guide and the template. A Jolokia policy cannot allow one operation alone (its `<allow>` section adds rights, `<deny>` takes precedence over it, both checked against Jolokia 2.6), so counting deadlocks means allowing `exec`, a choice left to the person, with Jolokia on the loopback and its password.

**Moving from another tool**: PRTG has no JMX sensor; people read Jolokia with HTTP sensors (HTTP, HTTP Advanced, HTTP Data Advanced, REST Custom, HTTP XML/REST Value) pointed at `/jolokia/`. Those become the Java check of that JVM, at the URL's address, port and path, `verify` for `https`, approximated (the JVM's usual metrics instead of the one value). A sensor type naming JMX or Jolokia (a custom one) maps the same. Zabbix's JMX templates ("Generic Java JMX", "Apache Tomcat by JMX", "Apache Kafka by JMX" and the older "Template App ... JMX") become one Java check per host at Jolokia's port, the host's JMX interface being the gateway's RMI port; their `jmx[...]` items are covered by it. A Prometheus job named after `jmx` (the JMX exporter, which has no port of its own) becomes the Java check of the exporter's machine.

Rejected: **the JMX exporter or the Zabbix Java gateway as the bridge**, each a separate process to install and run beside the JVM; **speaking RMI in Rust**, a Java serialization protocol whose clients have a long history of deserialization flaws; **an unverified `prefer` for HTTPS**, which would send the password to whoever answers; **reading Tomcat and Kafka only when asked**, which makes a Kafka broker's partitions depend on a setting people do not know of.

## Alternatives rejected

- **Scripts or plugins shipped as templates.** A check plugin (ADR-0103) runs in a WebAssembly sandbox whose one capability is HTTP, so it cannot speak a database's protocol; scripts need a runtime and a client on every server, and parse text. Built-in kinds are checked by the server before saving, run the same on agents and probes, and are tested against real servers.
- **Keeping a connection open between collections.** It saves a login a minute, but a pooled connection hides a server that refuses new ones (the most common failure: `max_connections` reached) and holds a slot that people count against their limits.
- **Credentials per device, as SNMP and vCenter have** (ADR-0149, ADR-0156). A server often runs two PostgreSQL clusters, or PostgreSQL and Redis with different accounts; a password per check fits, and the column already exists.
- **Docker from a probe over the engine's TCP API.** It needs the API opened on the network with a client certificate equal to root on every Docker host; the agent is already there.
- **Alerts written by the web interface after the check**, as for services. They would not exist for API clients without each one copying the list; a template served by the server, applied in the check's transaction, is the same for everyone.
- **`tiberius` for SQL Server.** Its rustls backend hard-codes aws-lc-rs; see above.
- **The AWS and Azure SDKs for cloud accounts.** `aws-sdk-ec2` and `aws-sdk-cloudwatch` with their runtime, and the Azure crates, add hundreds of dependencies and their own HTTP stacks for five read calls; Signature Version 4 is short, specified with test vectors, and `ring` is already in the workspace.
- **Azure Resource Graph for the machines**, as first planned. It needs the same Reader right but a query language whose answers are harder to bound, and it throttles per user; Resource Manager's list with `statusOnly=true` gives the power state in pages, and the network interfaces come in one more list.
- **Cloud checks from relays.** A site's relay rarely needs the Internet, and the secret of an account that may hold every machine of a customer stays on the central server.
- **sqlx's RSA support for MySQL 8 without TLS.** Its `rsa` crate has an unfixed timing advisory; MySQL 8 enables TLS by default, which this path uses.

## Consequences

- Databases, Redis and containers are watched from inside with a few fields filled in, and alerts that make sense from the first minute.
- Each check opens one connection per collection, the check's own session counted among the connections it reports.
- An agent with `sensors.port_targets` must list `127.0.0.1` (or the database's address) for these checks to run there; the check's error says so.
- Watching Docker gives the agent's account root's power on that host, which a person grants knowingly; the agent's code only reads.
- The real tests (`crates/apps/tests/real.rs`, with `scripts/apps-test.sh`, Tomcat and a Kafka broker with Jolokia among them) need Docker (and 2 GB of memory for SQL Server 2022, whose test builds an availability group of one replica without a cluster) and are not run by CI, which has no database containers; parsing, limits and failures are unit tested everywhere.
- SQL Server's own TDS client is code to keep, as RESP is; its tests cover the packets, the login and every token it reads, against a fake server and a real one.
- AWS accounts and Azure subscriptions are watched with read-only credentials, their machines in the same inventory as a vCenter's; a missing right shows on the account's page with the provider's message.
- CloudWatch's `GetMetricData` costs a little per running instance, which the guide states.
- Google Cloud stays on the roadmap as its own task, as do SQL Server's Windows sign-in, Kubernetes' inventory page and nodes matched to servers.
- A JVM is watched only with Jolokia loaded into it, a change to its start options that a person makes; the check counts deadlocked threads only if Jolokia's policy allows `exec`.
- A Kubernetes check reads every pod of the cluster each collection: about 1 MiB of JSON per 300 pods, within the 64 MiB and 10,000 objects of a list it stops at.
